# 本地开发与部署执行清单

本文记录开发流程的实施范围与验收要求。实施进度见第七节，尚未完成的命令与配置属于计划内容。

## 已确认的约定

| 项目 | 约定 |
| --- | --- |
| 开发系统 | macOS、Linux，Windows 成员在 WSL2 中开发 |
| 开发组织 | 每位成员独立运行完整本地环境，默认一个实例，支持显式配置多个实例 |
| 日常运行 | Go 和 Vite 在本机运行，Compose 默认启动 PostgreSQL |
| 执行资源 | Worker、用户容器、浏览器由平台按需创建 |
| 初始化 | 自动准备开发账号，真实演示资源通过独立命令创建 |
| Go 热重载 | 执行资源继续运行，后端重启后重新接管 |
| 完整退出 | 停止本次环境的全部进程与容器，保留数据 |
| 最终部署 | 一台 Ubuntu 24.04 LTS 服务器，按四核四 GiB 内存预算设计 |
| 发布产物 | 前端镜像、后端镜像分别构建，版本发布提供配套产物 |

## 一、运行结构与文件

本地 Go 使用 Air 监听源文件并重新编译，前端使用 Vite 热更新。开发入口使用 concurrently 管理进程，统一显示 Go、前端与类型检查输出。

| 文件或目录 | 职责 |
| --- | --- |
| compose.yaml | PostgreSQL 版本、健康检查、持久化等公共定义 |
| compose.dev.yaml | 本机数据库端口与开发环境配置 |
| compose.prod.yaml | 前端、后端、数据库与一次性迁移任务的部署配置 |
| .env.example | 完整配置模板、默认端口与配置说明 |
| .env.local | 当前成员的默认实例配置，保存在本机 |
| .air.toml | Go 编译、启动、监听范围与关闭行为 |
| web/Dockerfile | 构建前端静态文件并由 Nginx 提供服务 |
| Dockerfile | 构建 Go 管理服务与随版本发布的管理工具 |
| runtimes | workerd 与浏览器运行环境的构建定义 |
| .local | 按实例保存日志、进程信息、调试产物与本地状态 |

macOS 使用本机 Docker 引擎提供的 Linux 容器环境。WSL2 内保存源码并运行 Go、Node.js、Git 和项目命令，Windows 浏览器访问本地页面。

## 二、命令入口

| 命令 | 预期行为 |
| --- | --- |
| make setup | 安装锁定依赖、启用提交检查、准备开发工具，首次创建本地配置 |
| make doctor | 检查版本、Docker 连接、Compose、CPU 架构、配置、端口与实例占用 |
| make dev | 启动本实例数据库，等待健康，执行迁移与账号初始化，再启动 Go 和 Vite |
| make dev DEBUG=api | 使用 Delve 调试后端，保留同一套数据库、前端与退出行为 |
| make dev-status | 显示本实例进程、监听地址、数据库版本和执行容器状态 |
| make dev-logs | 查看带进程、实例与资源标识的日志 |
| make dev-stop | 幂等停止本实例全部进程与容器，保留持久化数据 |
| make db-status | 显示当前数据库版本与待执行迁移 |
| make db-migrate | 对指定环境显式执行迁移并返回实际结果 |
| make dev-reset | 经明确确认后清理指定开发实例的数据与资源 |
| make runtimes-prepare TARGET=workers 或 browser 或 all | 准备选定模块的锁定版本镜像 |
| make demo | 准备所需镜像，通过实际 API 创建并验证真实演示资源 |
| make test | 执行 Go 行为与 HTTP 测试 |
| make test-integration | 使用独立数据库和实际运行时执行集成测试 |
| make test-e2e | 使用真实浏览器与后端执行页面操作测试 |
| make check | 执行项目完整验证，输出各项检查结果 |
| make deploy-check | 在本机使用生产 Compose 配置验证前后端镜像和完整启动流程 |

make setup 重复执行保留已有配置与凭据。make dev 启动前显示实例名称和访问地址，端口占用或依赖不可用时直接返回具体错误。Vite 启用 strictPort。

依赖版本由仓库文件锁定，开发工具通过项目命令调用。首次准备下载依赖和镜像，后续复用本机缓存。镜像准备检查 amd64 与 arm64 支持情况，使用当前机器对应的架构，缺少支持时显示具体原因。

make demo 创建真实 Worker、持久化计数器、HTTP 容器和浏览器截图任务，校验实际输出。重复执行使用同一组演示资源标识。截图与验证结果保存在本实例的 .local 目录。

## 三、配置与网络

| 配置 | 用途与默认约定 |
| --- | --- |
| CLOUDLET_ENV | 区分 development、test、production |
| CLOUDLET_INSTANCE | 默认 default，多实例使用不同名称 |
| ENV_FILE | 默认 .env.local，显式指定其他实例的配置文件 |
| CLOUDLET_DATABASE_URL | 本机进程连接 127.0.0.1:15432，部署容器连接 postgres:5432 |
| DOCKER_HOST、DOCKER_CONTEXT | 确定实际 Docker 引擎，CLI、Go SDK 和测试工具保持一致 |
| CLOUDLET_RUNTIME_ACCESS | 本机采用 published，部署采用 network，由容器模块生成连接地址 |
| CLOUDLET_RUNTIME_NETWORK | 指定本实例执行容器加入的网络 |
| CLOUDLET_API_UPSTREAM | Vite 或 Nginx 使用的后端代理地址 |
| CLOUDLET_PUBLIC_ORIGIN | 管理页面公开地址 |
| CLOUDLET_GATEWAY_PUBLIC_URL | 工作负载地址生成所依据的公开入口 |
| 本机端口 | 前端 5173、API 8080、Gateway 8081、PostgreSQL 15432，均可显式配置 |

启动入口统一加载配置，再传入 Go、Vite、Compose 与管理命令。配置校验覆盖必填项、URL、端口和运行模式，错误说明包含字段名称。

前端统一请求 /api。本机由 Vite 转发，部署时由 Nginx 转发到后端容器。Nginx 通过启动时的环境变量生成代理配置，前端静态产物可在不同环境复用。数据库凭据与 Docker 连接配置只传给需要的进程或服务。

Gateway 使用容器模块返回的内部连接地址，同时对用户生成公开访问地址。本机使用 Docker 实际发布的端口，部署使用执行网络中的容器名称与服务端口。

本机开发服务与数据库发布端口绑定回环地址。数据库位于管理网络，执行资源位于执行网络，控制器按需连接两个网络。生产数据库与管理 API 使用内部地址，公开入口负责转发请求。浏览器控制端口保留在执行网络内部。

本地工作负载采用 .localhost 域名和 Gateway 端口访问。浏览器、CLI 与自动化测试分别验收域名和 Host 路由。浏览器执行容器访问同平台资源时使用执行网络内地址，页面测试进程从本机访问开发服务器。

DOCKER_HOST 与 DOCKER_CONTEXT 同时设置时返回配置冲突。显式指定其中一项时按该配置连接，未指定时使用当前 Docker context 对应的引擎。make doctor 验证 CLI、Go SDK、Testcontainers 能访问同一个实际引擎。

## 四、启动、热重载与完整退出

启动顺序为配置和端口检查、数据库健康检查、迁移、开发账号初始化、后端启动、前端启动与就绪检查。每项初始化完成后才进入下一项，失败触发本次启动资源的清理。

开发账号使用正常认证流程。首次初始化生成本地凭据，后续启动保留同一账号和密码。生产账号由显式管理命令创建。

迁移通过 goose 执行并使用 PostgreSQL 锁避免同时修改结构。生产迁移作为一次性任务执行，应用启动时验证所需版本。已有迁移文件保持稳定，结构变更新增迁移文件。

Go 热重载保留 Worker、用户容器和浏览器进程。新后端根据数据库元数据和 Docker 管理标签重新核对资源状态、路由和会话。编译失败时停止旧二进制并显示错误，修复后重新启动后端。

资源恢复使用实际容器状态，保留对象标识与持久化存储。浏览器控制连接支持按会话标识重新连接，后端重启后的调用继续使用原浏览器进程。过期浏览器会话按超时规则结束。资源创建中途发生后端退出时，重启核对已有容器，完成状态恢复与遗留资源处理。

Ctrl+C、开发入口异常退出和 make dev-stop 执行同一套停止流程：停止监听和应用进程，停止本实例执行容器，再停止 PostgreSQL。停止操作保留数据库、DO 状态和已保存的业务数据。

资源停止使用独立维护入口，具备直接访问 Docker 的能力。清理范围由实例标识、资源标识与管理标签共同限定，重复执行得到相同的停止结果。清理有明确超时，失败输出尚未停止的资源标识并返回错误。

再次 make dev 时恢复持久化数据和目标状态为运行的部署资源，浏览器临时会话重新创建。make demo 使用持久化资源标识核对真实结果。

## 五、多实例、数据与调试

显式多实例通过 ENV_FILE 指定独立配置，例如 ENV_FILE=.env.feature.local make dev。每个实例拥有独立端口、Compose 项目名、数据库数据卷、运行时数据卷与 .local 子目录。

动态创建的容器、网络和数据卷携带实例与资源归属标签。系统只允许同一实例存在一个活动控制器，重复启动时报告占用信息。

切换分支后检查数据库迁移版本。数据库版本超出当前代码支持范围时，启动返回明确错误。需要独立数据时建立另一个实例，需要重新初始化时显式执行 dev-reset。

dev-reset 只面向开发实例，确认内容包含目标实例名称与将清理的数据范围。数据库和运行资源的清理作为同一次操作核对，镜像缓存继续复用。

Delve 调试端口可配置且绑定本机回环地址。浏览器使用 source map 调试前端，平台日志携带请求与资源标识。账号凭据和完整数据库连接串不写入日志。

集成测试使用独立实例和数据库。任务结束后清理测试资源。CI 由实际改动选择检查范围，统一汇总结果，前后端镜像分别验证。

日常提交通过 CI 验证。需要验收部署方式时运行 deploy-check。版本发布通过标签触发，服务器部署作为显式操作执行。

## 八、最终部署核对

最终服务器按 Ubuntu 24.04 LTS、四核四 GiB 内存预算设计。部署前确认 CPU 架构、磁盘空间、域名、HTTPS 和访问范围。

前端镜像提供 Nginx 与静态页面，后端镜像提供 Go 服务和一次性管理命令。Compose 管理固定服务，平台管理按需创建的执行资源。

明确固定服务与执行资源的内存、CPU 和并发配额，浏览器默认并发一个会话，资源申请超出配置预算时明确返回错误。使用真实 Worker、DO、HTTP 容器和浏览器场景验证四核四 GiB 目标。

部署账户、数据库凭据与数据卷按服务器环境配置。Docker 管理连接只提供给控制器。镜像版本、迁移文件、数据库版本和运行时版本共同记录在部署说明中。

前后端发布产物记录各自镜像 digest，运行时镜像记录在同一版本清单中。服务器按清单拉取镜像。固定服务与执行容器配置日志轮转，过期浏览器会话和临时产物按保留期限清理。

部署流程包括拉取配套版本镜像、备份已有持久化数据、运行迁移、启动服务与执行验收。失败时明确停止部署流程，根据已保存的镜像版本与数据备份执行恢复步骤。

数据库使用 PostgreSQL 备份工具导出，DO 状态在对应运行时停止写入后备份持久化数据卷。备份包含资源元数据与运行时版本，并通过独立环境中的实际恢复验证。

最终验收覆盖登录、Worker 调用、DO 持久化、容器生命周期、浏览器截图，以及后端重启和整套服务重启。验收记录包含实际命令、版本和结果。
